DAY 03

模型格式

让模型成为可移植的中间表示

学习目标

能从计算图、权重张量、元数据三个角度阅读 ONNX、TFLite、GGUF 等格式。

核心概念

  • 计算图与拓扑排序
  • 权重布局与 dtype
  • opset、metadata 与版本兼容
  • 转换器、runtime 与后端的职责

嵌入式类比

模型格式类似 USB 描述符 + 数据包协议：描述符说明端点与能力，权重是 payload，runtime 负责把它落到具体控制器。

本章讲解

格式是模型的交接协议

ONNX 把图、初始化权重、输入输出和 opset 放进 ModelProto；它像 USB 描述符加 payload，而不是“任何 runtime 都必然能执行”的保证。runtime 必须支持该图声明的每个算子语义。

容器、IR 与后端要分层思考

ONNX 是交换 IR，TFLite/LiteRT 面向轻量 runtime，GGUF 是供 GGML 系执行器快速加载的模型容器。格式转换会改变 dtype、布局、常量折叠和算子版本，因此每一步都要检查 I/O 与数值误差。

流程图

Framework → Export IR → Converter → Optimizer → Runtime → Backend
 PyTorch       ONNX/TFLite/GGUF                     CPU/GPU/NPU

代码或命令示例

onnx.checker.check_model(model)
print(model.graph.input, model.graph.output)
# tflite / gguf 还要检查量化类型与 tokenizer metadata

动手实验

选一个小模型，分别列出输入输出、算子、权重 dtype、动态维度和 metadata。

工程陷阱

避免误判：“能用 Netron 打开”只说明文件可解析；不等于目标 runtime 支持该 opset、动态维度或自定义算子。

核心测试

完成 3 道单选题后提交；提交前不会显示答案。

1. ONNX opset 主要声明什么？
2. GGUF 最准确的描述是？
3. 转换后最可靠的第一项验证是什么？
