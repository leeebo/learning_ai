DAY 09

Tokenizer

理解文本如何变成模型可消费的整数流

学习目标

能解释 vocabulary、merges、special tokens、padding 与 token budget，并定位端侧分词开销。

核心概念

  • Unicode 与规范化
  • BPE/SentencePiece
  • 特殊 token 与 chat template
  • token id、位置编码与上下文长度

嵌入式类比

Tokenizer 是串口协议的 framing 层：人类文本先被切成稳定的帧编号，模型只认编号，不直接认字。

本章讲解

模型读 token id，不读 UTF-8 字符

Tokenizer 把文本规范化并编码为整数序列，类似串口协议先 framing 再解析 payload。中文、emoji 和代码的 token 成本由词表与编码规则决定，不能用字符数估算上下文。

聊天模板是模型输入协议

不同 instruct 模型可能使用不同控制 token。Hugging Face 文档强调错误模板会显著降低表现，并提醒模板已包含 special tokens 时不要在二次 tokenize 时重复添加。

流程图

UTF-8 text → normalize → tokenize → [BOS, 1203, 88, EOS] → embedding lookup

代码或命令示例

ids = tokenizer.encode("温度 28°C")
print(ids, len(ids))
prompt = template(system, user)
# token budget = prompt_tokens + generated_tokens

动手实验

选同一句中英文混合文本，比较不同 tokenizer 的 token 数；测量逐 token 编码与整段编码的差异。

工程陷阱

避免误判：把“同一句文本”直接拼接给不同聊天模型，或重复插入 BOS/EOS，常会造成模型角色混乱、首 token 异常或上下文预算失真。

核心测试

完成 3 道单选题后提交；提交前不会显示答案。

1. LLM 的上下文窗口通常限制什么？
2. 为什么应使用模型自带 chat template？
3. 先 apply_chat_template(tokenize=False) 再 tokenize 时通常要注意？
