DAY 14

性能分析

把“感觉慢”变成可定位的预算

学习目标

用端到端指标、分阶段计时、硬件计数器和功耗测量定位瓶颈。

核心概念

  • TTFT、tokens/s、p50/p95
  • 算子级 profile 与 trace
  • CPU 利用率、cache miss、带宽
  • 功耗、温度、降频
  • 准确率—延迟—能耗三维权衡

嵌入式类比

像抓 USB/网络协议问题：先看端到端时序，再缩小到阶段、包和 handler；单看平均吞吐会掩盖尾延迟。

本章讲解

先定义可复现的基准合同

固定模型版本、量化、prompt、输出上限、采样、线程、context、温度和供电状态。没有这些，两个 tokens/s 数字不可比较，就像未固定波特率和 payload 的吞吐测试。

分阶段测量才能定位

TTFT 覆盖首响应体验，inter-token latency 反映流式生成节奏，output token throughput 衡量整体产出。还要拆出预处理、prefill、decode、网络与后处理，并同时记录能耗和热状态。

流程图

Request → preprocess → prefill → decode×N → postprocess
  | wall time | p50/p95 | bytes moved | joules/token | thermal state

代码或命令示例

time_to_first_token = prefill_end - request_start
tokens_per_second = generated_tokens / decode_seconds
joules_per_token = energy_j / generated_tokens

动手实验

建立固定 prompt/温度/线程/电源条件的 benchmark 表；至少重复 5 次，报告中位数与 p95。

工程陷阱

避免误判：只报告平均 tokens/s 会掩盖长 prompt、热降频、首次加载和 p95 尾延迟；产品体验常由这些“非平均”路径决定。

核心测试

完成 3 道单选题后提交；提交前不会显示答案。

1. Time to First Token 的定义最接近？
2. 为何基准测试要 warm-up 并重复多次？
3. tokens/s 上升但 joules/token 变差，是否必然是成功优化？
