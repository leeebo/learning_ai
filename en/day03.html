Model Formats

Learning goal

HOW WE GOT HERE

Historical development

The evolution of model formats is fundamentally the story of handing an object internal to one framework to another software and hardware stack. Early models often depended on training code for interpretation; later, data-flow graphs, common operator semantics, and lightweight binary containers separated those concerns. Formats did not erase differences—they moved them from hidden source-code dependencies into inspectable schemas, opsets, and metadata.

2014

Caffe promoted model reuse through declarative networks and weight files

Caffe organized network structure, training configuration, and learned parameters as exchangeable artifacts, using layers as extension units. It demonstrated that a model could be shared and deployed outside one research script, while also exposing the problem of framework-specific layers tied to a format.

Original Caffe paper ↗
2015

TensorFlow expressed training and inference in one data-flow graph

The TensorFlow white paper represented machine-learning computation on heterogeneous systems as a stateful data-flow graph. Nodes, edges, device placement, and tensor flow became system-level interfaces, providing a clear foundation for later graph optimization, serialization, and cross-device execution.

2015 TensorFlow white paper ↗
2017

ONNX v1 published interoperability as a graph-and-operator contract

ONNX v1 released a production-ready format for multiple frameworks, promoting model transfer through an open graph format and operator sets. Exporters, converters, and runtimes could now collaborate around a common IR, although each still had to support the domains and opsets declared by a model.

Official ONNX v1 release announcement ↗
2017

TensorFlow Lite tightened format boundaries for mobile and embedded execution

TensorFlow Lite targeted small binaries, fast startup, and on-device acceleration. Model conversion was no longer only for interchange; it prepared structures that a constrained runtime could read directly. Supported operators, static memory planning, and hardware delegation began to influence model design upstream.

Official TensorFlow Lite announcement ↗
2023

GGUF emphasized single-file packaging, extensibility, and fast loading

GGUF, a model format for GGML-family runtimes, placed tensors and key-value metadata in an extensible binary container and superseded earlier GGML, GGMF, and GGJT formats. It showed that LLM deployment must preserve not just weights, but also reliable interpretation data such as architecture and tokenizer metadata.

Official GGUF specification ↗
Why it still matters today: Modern formats follow two complementary paths. IRs such as ONNX emphasize general computation graphs and operator semantics, while deployment containers such as LiteRT and GGUF stay closer to the loading and resource constraints of particular runtimes. Engineering choices should begin not with a file extension, but with the target backend’s support matrix, the input contract, variable shapes, and assets that must travel with the model.
BUILD INTUITION FROM A FAMILIAR SYSTEM

Illustrated analogy

Containers, manifests, and port rules in international shipping

A model is like a shipment of precision equipment changing carriers across countries. Weights are the cargo, the computation graph is the unloading and connection plan, metadata is the manifest, and the opset is the current edition of handling rules. Arriving at port only means the container can be identified; the destination still needs matching cranes and trained crews to assemble everything correctly.

📦 Shipping container → The binary model file packages tensors and structure
🗺️ Unloading route map → The computation graph defines node dependencies and tensor flow
📑 Manifest and rulebook → Metadata, IR version, opset, and custom domains
🏗️ Port cranes ↔ The runtime and backend must implement the required operators and dtypes

Where the analogy stops: Real model conversion does not move a sealed container unchanged. A converter may alter layouts, split operators, fold constants, or quantize tensors. The shipping analogy also cannot express floating-point non-associativity or dynamic control flow, so “all cargo present” never replaces numerical comparison with fixed inputs.

Chapter walkthrough

Separate a format into syntax, semantics, and companion assets

A schema only says how fields are encoded; operator specifications say what nodes must compute; tokenizers, label maps, and normalization parameters may live in metadata or external files. Successful parsing proves only that the syntax is valid. Missing operator semantics makes a runtime reject the model, while missing assets may let it run but misinterpret its outputs. List validation methods for every layer in the delivery checklist instead of recording only one model-file hash.

While reading a graph, track each value’s origin, lifetime, and variability

Graph inputs come from the caller, initializers usually store constant weights, and intermediate values are produced by nodes; symbolic or unknown values express dynamic dimensions. Topological order gives dependencies but not necessarily final execution order, because a runtime can reuse memory and schedule work in parallel. Mark which path produces each output, which dimensions may vary, and where shape inference fails.

IR, opset, and runtime versions are three different locks

The IR version constrains the model container and graph structure, an opset constrains signatures and semantics in a particular domain, and the runtime version determines implementation coverage. Lowering an opset is not changing an integer: if the older set has no equivalent expression, the converter must decompose a node or fail. A custom domain also requires shipping its implementation. A compatibility matrix should record all three versions with the target chip, not merely say “supports ONNX.”

Converters rewrite representations, so audit the change list

Conversion may expand a high-level operator into a subgraph, precompute constants, change NCHW to NHWC, or store weights in another dtype. Even mathematically equivalent rewrites can alter rounding, workspace, and backend partitioning. Preserve counts of added, removed, and replaced nodes in conversion logs, and map names for important intermediate tensors so an abnormal final output does not leave you guessing.

Build a model ABI test bundle instead of saving the model alone

Attach input names, shape ranges, dtypes, units, preprocessing and postprocessing versions, and several golden samples to every model version. Samples should include normal values, boundary shapes, and invalid inputs. CI first runs schema/checker validation, then loads the model in the target runtime and compares outputs within tolerance. If the model uses external weights or tokenizer files, validate relative paths and hashes as well, preventing a stable main file from hiding drift in companion assets.
